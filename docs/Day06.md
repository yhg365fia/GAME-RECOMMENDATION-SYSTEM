# 📅 Day06 — Steam Game Recommendation System

## 1. 오늘 한 것 (What I Did)

### 1-1. Content-Based Recommendation 기능 개선
- 기존 단일 게임 입력 방식을 **다중 게임 입력 방식**으로 변경
- 사용자가 여러 개의 게임을 입력하면 각 게임의 유사도를 계산하도록 알고리즘 수정
- 입력 종료를 위해 Enter 입력 시 반복문 종료 기능 구현

### 1-2. 다중 입력 추천 알고리즘 구현

**기존**
```
게임 1개
  ↓
코사인 유사도
  ↓
추천
```

**변경**
```
게임 여러 개
  ↓
각 게임별 코사인 유사도 계산
  ↓
평균 유사도 계산
  ↓
추천
```

이를 위해
- `similarity_list` 생성
- `cosine_similarity` 반복 수행
- `np.mean()`을 이용한 평균 유사도 계산

기능을 구현하였다.

### 1-3. 동일 이름(Game Name) 처리 기능 구현
같은 이름을 가진 게임이 존재하는 경우
```
Rainbow Six Siege
 [0]
 [1]
 [2]
 [3]
```
처럼 후보를 출력하고, 사용자가 원하는 게임을 직접 선택하도록 기능을 구현하였다.
이를 통해 잘못된 게임을 추천하는 문제를 줄일 수 있었다.

### 1-4. 추천 결과 중복 제거
추천 결과에서 같은 게임이 여러 번 추천되는 문제가 발생하였다.
이를 해결하기 위해 `used_names = set()`(이후 `used_appids`로 개선)를 활용하여, 이미 추천한 게임은 다시 추천하지 않도록 수정하였다.

### 1-5. 데이터 중복 제거
recommendation 데이터를 이용하다 보니, 유저-게임 조인 구조 특성상 **같은 게임이 사용자 수만큼 중복 존재**한다는 문제를 발견하였다.
이를 해결하기 위해 `drop_duplicates()`를 이용하여 중복 게임 제거를 적용하였다.

### 1-6. 추천 시스템 구조 재설계
기존에는
```
Game → Index
```
정도로만 생각하고 있었지만, 오늘은 추천 시스템 내부 구조를 다시 정리하였다.
```
Game Name
  ↓
AppID
  ↓
Index
  ↓
TF-IDF Vector
  ↓
Similarity
  ↓
추천 Index
  ↓
AppID
  ↓
Game Name
```
실무에서는 AppID를 중심으로 관리하는 이유도 함께 이해하였다.

### 1-7. 데이터 로딩 성능 최적화
- CSV를 그대로 읽으면 파싱 자체가 오래 걸린다는 문제를 발견
- 필요한 컬럼만 `usecols`로 선택, `dtype`을 미리 지정하여 pandas 타입 추론 시간 단축
- 원본 CSV를 매번 다시 읽지 않도록 **parquet 캐싱** 구조 도입 (`load_games`, `load_train`, `load_test`에 적용)

### 1-8. 다양한 입력 테스트
추천 결과를 확인하기 위해 PUBG, Battlefield, Phasmophobia, Resident Evil, Outlast 등 다양한 게임을 입력하여 추천 결과를 테스트하였다.

### 1-9. 추천 결과 분석
단순히 추천 결과만 확인하는 것이 아니라
- 왜 이 게임이 추천되었는지
- 장르가 얼마나 반영되었는지
- 공포와 FPS가 동시에 반영되었는지

등 추천 결과를 직접 분석하기 시작하였다.

### 1-10. 실전 디버깅 — "중복 제거가 안 먹히는" 버그 추적
`drop_duplicates(subset="Name")`를 적용했음에도 추천 결과에 같은 이름의 게임(`Tom Clancy's Rainbow Six® Siege X`)이 5개나 중복 출력되는 문제가 발생하였다.

원인을 좁혀나간 과정:
1. 공백/대소문자 차이 의심 → `str.strip()` 적용
2. 유니코드 정규화 차이(`®`, 어퍼스트로피 등) 의심 → `repr()`로 눈에 안 보이는 문자 차이 확인
3. `repr()`로 찍어봐도 문자열이 완전히 동일한데도 dedup이 안 먹히는 상황까지 도달
4. → **코드 로직 문제가 아니라, "수정한 코드가 실제로 실행되고 있는가" 자체를 의심해야 하는 상황**임을 파악 (인덱스가 `reset_index(drop=True)` 적용 후에도 `6225, 7101, 26241...`처럼 그대로 남아있던 것이 결정적 단서)
5. Jupyter 커널 모듈 캐싱, 파일 저장 여부, 실행 경로 등 **실행 환경 자체를 점검**하는 디버깅 순서를 밟는 중

## 2. 오늘 배운 것 (What I Learned)

### 2-1. TF-IDF의 동작 원리
기존에는 "TF-IDF를 만든다" 정도로만 이해하고 있었지만, 오늘은
```
게임 설명 → TF-IDF → 숫자 벡터 생성 → 코사인 유사도 계산
```
이라는 전체 과정을 이해하였다.

### 2-2. tfidf_matrix의 역할
`tfidf_matrix`는 모든 게임의 특징을 숫자로 변환하여 저장한 행렬이며, 추천 시에는 `tfidf_matrix[idx]`를 이용하여 특정 게임의 특징 벡터를 가져온다는 것을 이해하였다.

### 2-3. Index를 사용하는 이유
처음에는 "게임 이름으로 하면 되지 않을까?"라고 생각했지만, 추천 알고리즘은 행 번호(Index)를 이용하여 벡터를 관리하는 것이 훨씬 효율적이라는 점을 이해하였다.
- `tfidf_matrix`는 **numpy/sparse 배열**이라 key가 아니라 **위치(0, 1, 2...)로만 접근 가능**하다는 것,
- 그래서 `mean_scores`, `argsort()`, `sim_indices`가 전부 "배열의 위치 = idx"라는 하나의 규칙 위에서 안전하게 서로 대응된다는 것을 단계별로 추적하며 이해하였다.

### 2-4. AppID의 중요성
게임 이름은 중복될 수도 있고 변경될 수도 있다. 하지만 AppID는 게임마다 하나만 존재하는 고유 번호이므로, 추천 시스템에서는 AppID를 중심으로 관리하는 것이 안정적이라는 것을 배웠다.
- `app_id`(의미 있는 고유 ID)와 `idx`(행렬 내 위치)가 서로 다른 개념이라는 것,
- 이 둘을 연결해주는 `game_to_idx` 딕셔너리의 역할을 이해하였다.
- 사용자 입력(Name) → AppID 변환 → 내부 처리(AppID 기준)로 **책임을 분리**하는 설계 방식도 적용해보았다.

### 2-5. argsort()[::-1]
유사도가 큰 순서대로 추천하기 위해 `argsort()[::-1]`을 사용한다는 것을 이해하였다. (오름차순 정렬 결과를 뒤집어 내림차순으로 만드는 원리)

### 2-6. iterrows()
DataFrame을 행(Row) 단위로 순회하는 방법을 학습하였다.

### 2-7. strip()
사용자 입력 시 앞뒤 공백을 제거하기 위해 `strip()`을 사용하는 이유를 이해하였다. 다만 이번 트러블슈팅을 통해 **`strip()`만으로는 유니코드 정규화 차이까지는 못 잡는다**는 한계도 함께 알게 되었다 (`unicodedata.normalize` 필요성).

### 2-8. drop_duplicates()
중복 데이터를 제거하는 방법과, 콘텐츠 기반 추천에서는 게임 하나당 하나의 벡터만 필요하다는 이유를 이해하였다.
- 유저-게임 조인 데이터로 TF-IDF를 학습하면 같은 게임 텍스트가 유저 수만큼 중복되어 **IDF 통계 자체가 왜곡될 수 있다**는 문제를 짚어보고, "콘텐츠 계산용 meta(게임 단위 dedup)"와 "평가용 user_history(유저 단위, split용)"를 분리해서 관리해야 한다는 설계 원칙을 정리하였다.

### 2-9. 평균 유사도의 특징
다중 게임 입력 시 현재는 평균 유사도를 이용하여 추천하고 있다. 하지만 실험 결과, 공포게임 + FPS를 입력했을 때 공통 특징을 가진 게임보다 한쪽 장르에 매우 가까운 게임이 상위에 추천되는 경우가 발생하였다.

### 2-10. 캐싱의 함정
전처리 함수(`preprocess()`) 로직을 고쳤는데도 결과가 안 바뀌는 문제를 겪었다. 원인은 **캐시 파일(parquet)이 옛날 버전을 그대로 들고 있어서**였다. "캐싱은 속도를 벌어주지만, 코드가 바뀌면 캐시도 같이 갱신해야 한다"는 것을 실전에서 체감하였다.

### 2-11. 개발 환경 이슈
- 터미널 실행 방식(Task 실행 vs 터미널 직접 실행)에 따라 색상 표시 등 UX가 달라진다는 것을 알게 되었다.
- `settings.json`에 `terminal.integrated.defaultProfile.windows` 같은 설정을 직접 추가/수정하는 경험을 하였다.

### 2-12. 앞으로 개선할 점 발견
이번 테스트를 통해 현재 추천 방식의 한계를 확인하였다. 향후에는
- 평균 대신 다른 유사도 집계 방식
- 태그 가중치 조정
- Genres와 Tags의 중요도 차등 적용
- 하이브리드 추천

등을 적용하면 추천 품질을 더욱 높일 수 있을 것이라는 개선 방향을 도출하였다. 또한 진행 중인 dedup 버그(실행 환경/모듈 캐싱 이슈)를 마저 해결하고, 평가 지표(Recall@K, Hit Rate) 기반의 정량적 검증 단계로 넘어갈 예정이다.
