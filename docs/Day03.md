# 📅 Day03 - Data Refinement & TF-IDF Vectorization

## 📌 Overview

오늘은 콘텐츠 기반 추천 시스템(Content-Based Recommendation)의 핵심인 **데이터 전처리(Data Preprocessing)** 와 **TF-IDF 벡터화(Vectorization)** 를 진행하였다.

오늘 작업은 단순히 데이터를 정리하는 것보다 **추천 시스템의 방향을 설계하는 과정**에 가까웠다.

어떤 Feature를 사용할 것인지, 어떤 데이터는 제외할 것인지, 결측치를 어떻게 처리할 것인지, 추천 성능을 높이기 위해 어떤 방식으로 Feature Engineering을 진행할 것인지에 대해 많은 고민을 하였다.

또한 책에서 사용하는 예제와 실제 대용량 데이터셋의 차이점을 직접 경험하면서 추천 시스템 구현 방식도 수정하게 되었다.

# 1. Data Analysis

우선 추천 시스템에서 사용할 메타데이터를 전체적으로 분석하였다.

현재 사용할 수 있는 주요 Feature는 다음과 같았다.

- Genres
- Tags
- Categories
- About the Game

각 컬럼의 결측치와 데이터 형태를 확인한 결과

Genres, Tags, Categories는 비교적 일정한 형식을 가지고 있었지만

About the Game은 상당히 많은 문제점을 가지고 있었다.

대표적으로

- 설명 길이가 게임마다 매우 다름
- 중국어, 영어 등 여러 언어가 혼재
- HTML 태그 및 특수문자 존재
- 게임마다 작성 형식이 일정하지 않음

문자열 길이를 확인한 결과

최대 약 **89,000자**에 가까운 데이터도 존재하였다.

길이가 긴 데이터 상위 10개를 출력하여 직접 확인한 결과

단순한 설명이 아니라

HTML, 다국어, 긴 소개문 등이 포함되어 있었다.

현재 단계에서 이 데이터를 그대로 사용하는 것은

추천 성능보다 노이즈가 더 커질 가능성이 있다고 판단하였다.

따라서 Baseline 모델에서는

```
Genres
Tags
Categories
```

세 개의 Feature만 사용하는 것으로 결정하였다.

About the Game은

후속 Feature Engineering 단계에서

텍스트 정제 및 언어 처리를 수행한 후

성능을 비교하기로 하였다.

# 2. Missing Value Strategy

결측치 처리 방법에 대해서도 여러 가지 방법을 고민하였다.

기존에는 단순히

```python
fillna("")
```

만 수행하였지만

결측치가 많은 게임은

추천에 사용할 정보가 부족하기 때문에

추천 품질을 낮출 수 있다는 점을 고려하였다.

처음에는

결측치가 많은 데이터를 제거하는 방법도 생각하였다.

하지만 추천 시스템에서는

가능한 많은 게임을 유지하는 것이 중요하기 때문에

무조건 제거하는 것은 적절하지 않다고 판단하였다.

최종적으로 다음과 같은 전략을 세웠다.

| 결측치 개수 | 처리 방법 |
|------------|----------------------------|
| 4개 이상 | 데이터 제거 고려 |
| 3개 | 큰 패널티 적용 |
| 2개 | 중간 패널티 적용 |
| 1개 | 작은 패널티 적용 |
| 0개 | 패널티 없음 |

여기서 중요한 점은

패널티를 **전처리 단계에서 적용하는 것이 아니라**

추천 결과를 정렬하는 **Ranking 단계에서 적용하기로 결정한 것이다.**

예를 들어

```
최종 점수

=

Cosine Similarity

×

Penalty
```

와 같은 방식으로

추천 결과에만 영향을 주도록 설계하였다.

이렇게 하면

언제든지 패널티 값을 변경하거나

실험을 수행하기 쉬우며

데이터 자체는 그대로 유지할 수 있다는 장점이 있다.

---

# 3. Duplicate Analysis

추천 시스템에서는

중복 데이터도 중요한 요소이다.

먼저

게임 이름(Name)의 중복을 확인한 결과

약 **1,174개의 중복 이름**이 존재하였다.

하지만

Steam의 AppID는 모두 서로 달랐으며

같은 이름이라도

다른 게임인 경우가 존재하였다.

대표적인 예시는

```
2048
```

이라는 이름을 가진 게임이었다.

이름은 같지만

AppID와 메타데이터가 서로 다른

별개의 게임이었다.

따라서

추천 시스템에서는

게임 이름이 아닌

Steam AppID를 기준으로 관리하는 것이

더 안전하다는 점을 알게 되었다.

# 4. Feature Construction

추천 시스템에서 사용할 Feature를 생성하였다.

사용한 컬럼은

- Genres
- Tags
- Categories

이다.

각 컬럼 내부에는

쉼표(,)로 여러 개의 태그가 연결되어 있었기 때문에

쉼표를 공백으로 변경하였다.

```
Action,Adventure

↓

Action Adventure
```

이후

세 개의 컬럼을 하나의 문자열로 결합하였다.

```
Genres

↓

Tags

↓

Categories

↓

combined_features
```

이렇게 생성한

combined_features가

추천 시스템에서 사용하는 대표 Feature가 된다.

---

# 5. Feature Length Analysis

combined_features를 생성하면서

문장 길이가 게임마다 상당히 다르다는 점도 확인하였다.

예를 들어

어떤 게임은

```
Action Adventure
```

정도의 짧은 Feature만 가지는 반면

어떤 게임은

수십 개 이상의 Tags를 포함하고 있었다.

처음에는

긴 문장이

추천 결과에 더 큰 영향을 주는 것이 아닌지 의문이 들었다.

하지만 TF-IDF는

단순히 문자열 길이를 비교하는 방식이 아니라

각 단어의 중요도를 계산하는 방식이기 때문에

문장의 길이가 다르더라도

어느 정도 영향을 보정해 준다는 점을 알게 되었다.

물론

정보가 지나치게 적은 게임은

추천 정확도가 낮아질 가능성이 있기 때문에

향후 Ranking 단계에서

패널티를 적용하는 것도 고려하기로 하였다.

---

# 6. TF-IDF Vectorization

생성한

combined_features를 이용하여

TF-IDF Vectorizer를 적용하였다.

```python
tfidf = TfidfVectorizer(
    lowercase=True
)

tfidf_matrix = tfidf.fit_transform(meta["combined_features"])
```

벡터화 결과

```
(117560, 544)
```

- 게임 수 : **117,560**
- Feature 수 : **544**

TF-IDF를 사용하면서

단순히 문자열을 숫자로 바꾸는 것이 아니라

각 단어의 중요도를 계산하여

벡터를 생성한다는 점을 다시 확인하였다.

또한

TF-IDF는

전체 데이터에서 자주 등장하는 단어의 가중치는 낮추고

특정 게임에서만 등장하는 특징적인 단어에는

더 높은 가중치를 부여한다는 점도 이해하게 되었다.

---

# 7. Memory Issue

책에서 사용한 방식처럼

```python
cosine_similarity(
    tfidf_matrix,
    tfidf_matrix
)
```

를 이용하여

전체 Cosine Similarity Matrix를 생성하려고 하였다.

하지만

```
MemoryError

Unable to allocate 103 GiB
```

오류가 발생하였다.

원인을 분석해 보니

117,560개의 게임에 대해

모든 게임 간의 유사도를 계산하려 했기 때문이었다.

즉

```
117560 × 117560
```

크기의 행렬을 생성해야 했고

약 100GB 이상의 메모리가 필요하였다.

이를 통해

책에서 사용하는 예제와

실제 대용량 데이터는

구현 방식이 달라져야 한다는 점을 알게 되었다.

---

# 8. Solution

전체 유사도 행렬을 저장하는 방식 대신

추천 요청이 들어왔을 때

```
사용자 입력

↓

게임 선택

↓

선택한 게임과

전체 게임만 비교

↓

Top-N 추천
```

방식으로 변경하기로 결정하였다.

이 방식은

```
1 × 117560
```

크기만 계산하기 때문에

메모리 사용량이 매우 적으며

실제 서비스에서도 많이 사용하는 방식이다.

훨씬 효율적이라는 점을 알게 되었다.

또한

전처리 역시

모든 것을 처음부터 완벽하게 수행하기보다

실험을 통해 점진적으로 개선하는 과정이라는 점도 배울 수 있었다.
