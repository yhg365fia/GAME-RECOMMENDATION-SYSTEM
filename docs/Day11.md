# Day11 회고 — User-based CF 데이터 누수 디버깅 및 평가

## 1. 오늘 한 일 요약

- User-based CF 평가 결과에서 비정상적으로 높은 지표(Precision@10 0.6254 등)를 발견하고 원인 추적
- 여러 단계를 거쳐 데이터 누수의 실제 원인을 특정: `run_evaluation()` 호출 시 `user_to_idx` 인자를 넘기지 않아, `exclude_user_idx`가 항상 `None`으로 고정되고 자기 자신 제외 로직이 한 번도 실행되지 않았던 버그
- 버그 수정 후 소규모(17명) → 중규모(37명) → 100명(362명 유효) 표본으로 순차적으로 재평가
- Precision@10 지표 계산 방식(분모가 되는 `recommended_ids`의 정의) 및 `n_recommended`가 유저마다 들쭉날쭉한 이유 분석
- 최종적으로 100명(그룹당) 규모 평가 결과를 확보하고, User-based CF가 이 데이터셋에 부적합하다는 결론에 도달

## 2. 디버깅 과정 (시간순 — 가설과 깨달음)

**1) 이상 징후 포착**
Content-based(Precision 0.0268)와 비교해, User-based CF 첫 평가 결과(Precision@10 0.6254)가 비정상적으로 높다는 걸 스스로 "말이 안 된다"고 판단하고 원인 추적을 시작함.

**2) 첫 번째 가설 — 데이터 누수 (원인은 맞았음)**
`interaction_matrix`가 train/test 미분리 원본으로 만들어져 있어, 평가 대상 유저 본인의 데이터가 이웃 후보 풀에 그대로 남아있다는 걸 발견함. Day08~09 코드와 비교하며 "예전엔 `user_sim[i, orig_idx] = 0`으로 자기 자신을 제거했는데, `recommend()` 인터페이스로 리팩토링하면서 이 제거 로직이 통째로 빠졌다"는 근본 원인을 스스로 찾아냄.

**3) 1차 수정 — 그런데 결과가 똑같음**
`recommend()`에 `exclude_user_idx` 파라미터를 추가하고 자기 자신 유사도를 0으로 만드는 로직을 넣었음. 그런데 수정 후에도 지표가 이전과 완전히 동일하게 나옴. 이 시점에서 "자기 자신 제외 후에도 지표가 다 완전 똑같이 나왔다"는 사실을 놓치지 않고 계속 의심함 — 이게 이후 진짜 원인을 찾는 데 결정적인 단서가 됨.

**4) 원인 재탐색 — 여러 가설을 순차적으로 검증하며 소거**
"완전히 동일하다"는 현상을 설명하기 위해 다음 가설들을 순서대로 세우고 하나씩 코드로 검증함:
   - 가설 A: 함수 시그니처는 고쳤지만 호출부에서 `exclude_user_idx`를 안 넘기고 있는 게 아닌가 → `evaluate_user`, `run_evaluation` 코드를 직접 열어 확인 → 정상적으로 연결되어 있음을 확인
   - 가설 B: `user_to_idx`와 `interaction_matrix`의 인덱스가 서로 어긋난 게 아닌가 (row 순서 불일치) → 직접 `idx_to_user_check[test_user_idx] == test_user_id` 로 역검증 → `True`로 확인되어 기각
   - 가설 C: Jupyter에서 클래스 정의를 수정한 뒤 오래된 객체(recommender 인스턴스)를 그대로 쓰고 있는 게 아닌가 → 재실행 필요성 인지
   - 가설 D: `sims[0, exclude_user_idx] = 0`이 실제로 top-k 이웃 선정에 반영되는지 → 자기 자신과의 유사도를 직접 계산해보니 0.7746, 전체 유저 중 1위(자기보다 유사도 높은 유저 0명)라는 걸 확인 → 이론적으로는 반드시 제외 효과가 나타나야 하는 상황임을 재확인

**5) 진짜 원인 발견 — 호출의 가장 바깥쪽**
`main.py`에서 실제로 쓰던 코드를 다시 보여준 순간, `run_evaluation(recommender, user_history, sampled_users, top_n=10)` 호출에서 **`user_to_idx` 자체를 아예 넘기지 않고 있었다**는 걸 확인함. 함수 내부 로직(`recommend`, `evaluate_user`, `run_evaluation` 정의부)은 모두 정확했는데, 정작 이걸 실행하는 최상위 호출 한 줄에서 인자가 빠져 있었던 것. 지금까지 "내부 로직"만 계속 의심했던 것과 달리, 문제는 항상 "호출부"에 있었다는 걸 이 순간 깨달음.

**6) 수정 및 검증 — 규모를 늘려가며 확인**
`user_to_idx=user_to_idx`를 명시적으로 전달하도록 수정. 17명 → 37명 → 100명(그룹당) 순으로 표본을 늘려가며 재평가함. Precision이 0.6254 → 0.0529 → 0.0545 수준으로 정상화되는 걸 단계적으로 확인하며 버그가 실제로 해결됐음을 검증함.

**7) 새로운 의문 제기 — precision 해석 자체에 대한 의심**
지표가 정상화된 후에도 "test 3개 중 다 맞혀도 이론상 precision 최댓값이 0.3인데, 이 계산이 맞는 건가"라는 의문을 스스로 제기함. `recommended_ids`(분모)가 항상 10개가 아니라 `n_recommended`가 유저마다 1~10개로 들쭉날쭉하다는 걸 확인하고, 이게 지표 해석을 왜곡시킬 수 있다는 걸 파악함.

**8) 결론 도출과 재검토**
review_group(리뷰 수)이 클수록 성능 지표가 함께 오르는 패턴을 발견하고, 이를 근거로 "User-based CF는 sparse한 데이터에서 성능이 떨어진다 → 이 프로젝트 데이터셋에는 부적합하다"는 결론을 세움. 이후 이 결론과 세부 해석(recall vs precision 비교, NDCG 비교 등)을 다시 데이터와 대조하며 일부는 스스로 수정함 (3-2 참고).

## 4. 지표 결과 분석

### 3-1. 내가 직접 분석/판단한 부분

- **review_group이 클수록(리뷰 수가 많을수록) precision, recall, hit_rate, ndcg가 전반적으로 상승하는 경향**을 확인함. 특히 46-78개 그룹에서 precision(0.098)이 다른 그룹 대비 뚜렷하게 높게 나타남.
- 이 상승 패턴이 우연이 아니라 **User-based CF가 sparse한 유저(리뷰 적은 유저)일수록 이웃 매칭 정보가 부족해 성능이 떨어지는 구조적 한계**를 보여준다고 판단함.
- `n_recommended`(추천 후보 개수)가 유저마다 최소 1개~최대 10개로 크게 들쭉날쭉하다는 점을 근거로, 현재 precision·recall 수치가 분모(추천 개수)가 유저마다 다른 상태에서 단순 평균된 것이라 지표의 해석 신뢰도에 한계가 있다는 점을 스스로 지적함.
- 유사도가 0 이하(음수/0)인 이웃은 추천 후보에서 제외하는 현재 로직 특성상, 데이터가 희소하거나 유사한 이웃이 없는 유저는 추천 후보 자체가 1~2개로 줄어들고, 이 경우 우연히 하나만 맞아도 precision이 비정상적으로 튈 수 있다는 가능성을 스스로 제기함.
- 최종 결론: **User-based CF는 상호작용 매트릭스가 극도로 희소한 이 Steam 데이터셋에는 적합하지 않으며, item-based CF로 전환이 필요하다.**

### 3-2. Claude 도움을 받아 확인/수정한 부분

- **Recall과 Precision 크기 비교가 실제 데이터와 맞지 않았던 부분**: 처음에는 "user-base는 recall이 precision보다 잘 나오는 특징이 있다"고 판단했으나, 실제 전체 평균(Precision 0.0545 > Recall 0.0427)과 그룹별 추이(26-45개 그룹부터 이미 precision이 recall 역전)를 대조한 결과 반대로 확인됨. 일반화된 결론으로 삼기엔 근거가 부족했던 부분을 수정함.
- **"46-78개 그룹에서 precision이 갑자기 오른 게 설명이 안 된다"는 의문**: `n_recommended` 표(그룹별 평균 추천 개수: 5.74 → 6.47 → 8.03 → 8.54)와 나란히 놓고 보면, 추천 후보가 잘 채워지는 그룹일수록 precision도 함께 오르는 일관된 패턴이라는 것을 확인함. 우연이 아니라 결론(sparse 데이터에 CF가 약함)을 뒷받침하는 근거로 재해석함.
- **NDCG와 Recall을 직접 비교해 "랭킹이 아예 무의미하진 않다"고 판단한 부분**: 두 지표는 계산 방식 자체가 다르므로 크기를 직접 비교해 결론의 근거로 삼기보다는, "완전 무작위 추천은 아니라는 정황" 정도의 참고 수준으로 표현을 낮추는 게 더 정확하다는 점을 짚음.
- **분모(n_recommended)가 유저마다 다른 문제를 통계적으로 보완할 구체적 방법(micro-average, 상관계수 검정)이 다음 할 일로 제시됨**: 현재 방식(macro-average, 유저별 precision을 개별 계산 후 단순 평균)은 추천 개수가 적은 유저도 동일 가중치로 평균에 반영되는 한계가 있어, `hits.sum() / n_recommended.sum()`으로 계산하는 micro-average를 추가로 확인해볼 필요성을 확인함. 또한 "review_group이 클수록 성능이 좋다"는 관찰을 상관계수(Pearson correlation)로 정량 검증하는 방법을 제안받음.

## 5. 오늘 발견한 핵심 버그 (기록용)

**버그**: `run_evaluation(recommender, user_history, sampled_users, top_n=10)` 호출 시 `user_to_idx`를 넘기지 않아, 함수 내부의 `user_idx = user_to_idx.get(user_id) if user_to_idx is not None else None`이 항상 `None`을 반환. 그 결과 `exclude_user_idx`가 `recommend()`까지 항상 `None`으로 전달되어, 자기 자신을 이웃에서 제외하는 로직이 한 번도 실행되지 않음.

**증상**: 자기 자신의 데이터(train+test 전체)가 이웃 후보에 그대로 남아있어, 유사도가 가장 높은 이웃(사실상 자기 자신)을 통해 test 정답이 예측 점수에 직접 새어 들어감. 이로 인해 Precision@10이 0.6254까지 비정상적으로 높게 나옴.

**수정**: `run_evaluation(..., user_to_idx=user_to_idx, top_n=10)`로 명시적으로 전달. 수정 후 Precision@10이 0.0545 수준(content-based의 0.0268과 유사한 자릿수)으로 정상화됨.

**교훈**: 클래스 내부 로직(`recommend()`)과 그 로직을 호출하는 함수(`evaluate_user`, `run_evaluation`)는 모두 개별적으로는 정확했음에도, 최상위 호출부에서 인자 하나를 누락하면서 전체 로직이 무력화됨. 여러 파일/함수로 나뉜 파이프라인에서는 함수 내부보다 **호출 체인(누가 누구를 어떤 인자로 부르는지)을 먼저 추적하는 디버깅 습관**이 필요함을 체감함.

## 6. 디버깅 방법론 정리 (Outside-In vs Inside-Out)

오늘 겪은 문제를 계기로, 디버깅 접근법을 두 가지로 구분해서 정리함.

**Outside-In (바깥→안, 기본 접근)**: 함수 호출부, 인자 전달, 파이프라인 전체 흐름부터 확인하는 방식. "로직을 수정했는데 결과가 전혀 안 바뀔 때"는 로직 자체보다 호출 자체가 안 됐거나 잘못된 값이 들어갔을 확률이 높으므로 이 경우 기본값으로 삼아야 함. 오늘 겪은 `user_to_idx` 미전달 버그가 정확히 이 케이스였음.

**Inside-Out (안→밖, 예외적 상황)**: 입출력이 이미 확정된 상태에서 특정 함수/알고리즘 자체의 연산이 의심될 때(행렬 shape 오류, 수식 오류 등) 적합.

**판단 기준**: "코드를 고쳤는데 결과가 똑같다"는 신호가 나오면 Outside-In으로 전환. 이 원칙을 앞으로 디버깅 첫 단계 습관으로 삼기로 함.

**터널 비전 방지 수칙 (다음부터 적용)**:
- 시간 제한: 한 함수/로직에서 20~30분 이상 못 찾으면 무조건 시선을 호출부·입력값으로 돌리기
- 코드 수정 전 3가지 자문: ① 이 함수가 실제로 실행되는가(로그 확인) ② 전달한 인자가 생각한 값·형태가 맞는가 ③ 수정 후 실행한 게 진짜 내 변경사항이 반영된 결과인가
- 막히면 문제 상황을 말로 풀어 설명해보기(러버덕 디버깅) — 설명하는 과정에서 놓친 지점이 드러나는 경우가 많음

## 7. 성찰 및 느낀 점

- 코드 자체(각 함수의 로직)는 어렵지 않았는데, 여러 파일/함수로 파이프라인이 나뉘면서 "인자가 끝까지 제대로 전달되는지"를 추적하는 데 예상보다 훨씬 오래 걸림. 이는 실력 부족이 아니라, 시스템 관점의 디버깅 경험이 아직 부족했기 때문이라는 걸 이해함.
- 문제 상황에서 "코드를 고쳤는데 결과가 똑같다"는 사실을 끝까지 놓치지 않고 계속 의심한 것이 결국 진짜 원인을 찾는 데 결정적이었음. 직감(어딘가 이상하다는 느낌)이 있었지만 정확히 어디인지 말로 설명하지 못했던 부분은, 로그와 값을 직접 찍어 확인하는 과정을 통해 명시적 근거로 검증할 수 있었음.
- 앞으로는 결과가 이상할 때 함수 내부 로직부터 파기보다, **먼저 호출부 전체를 훑으며 인자가 실제로 의도대로 전달되고 있는지부터 확인하는 습관**을 들이기로 함.
- AI(Claude)를 활용하는 방식에 대해서도 점검함: 오늘은 스스로 이상 징후를 포착하고, 가설을 세우고, 코드를 직접 실행/확인하는 과정을 거친 뒤 막히는 지점에서 도움을 받는 방식으로 진행됨. 이 비율(스스로 판단 → 막히면 좁혀서 질문)을 앞으로도 유지하는 것이 실력 성장에 유리하다는 결론을 내림.
- User-based CF의 한계를 데이터를 직접 돌려보며 몸으로 겪었는데, 다음 프로젝트부터는 모델을 돌리기 전에 데이터의 sparsity, 유저당 평균 상호작용 수 등을 먼저 계산해 "이 모델이 이 데이터에 적합한가"를 사전에 예측하고 검증하는 능력을 기르고 싶다는 목표를 세움.
